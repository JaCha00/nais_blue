# NovelAI Diffusion V5 Full 누적 결론

> 최종 갱신: 2026-08-22 · 공식 확인, 반복 관찰과 미검증 가설을 분리한다.

## 기존 결론의 용어 보정

1. `각 태그의 학습량`은 직접 측정할 수 없으므로 `모델 내부 재현 강도`라고 부른다. 이는 실제 학습 표본 수뿐 아니라 캡션 일관성, 중복 제거, 샘플링, 태그의 시각적 응집도에 함께 좌우될 수 있다.
2. Danbooru 게시글 수는 재현 강도의 유용한 프록시지만 학습량 공식은 아니다. 공식 UI의 Tag Knowledge 표시, NAI 학습 시점과 현재 게시글 수가 서로 다를 수 있다.
3. 현재 확인한 첫째·둘째·셋째 역할은 세 artist 태그 사이의 상대 순서다. 임의로 긴 전체 프롬프트의 절대 상단·중단·하단이 같은 역할을 한다는 일반화는 T01 결과 전까지 보류한다.
4. 문자열로 적은 `scope`, `background`, `target` 라벨은 약한 힌트지만, UI의 Character Prompt와 Character Positioning은 실제 별도 conditioning 경로이므로 같은 등급으로 취급하지 않는다.

현재 영향 모델은 다음처럼 기록한다.

```text
모델 내부 재현 강도 > 상대적 토큰 순서 ≥ 숫자 가중치·중복 > 문자열형 범위 라벨
```

이 순위는 전역 스타일 토큰에 대한 작업 가설이며 모든 개체·관계 토큰에 확정 적용하지 않는다.

## 스타일 태그의 전역성과 상대 순서

- artist 태그는 어떤 섹션이나 대상 라벨 아래에 두어도 그림 전역에 영향을 미쳤다. 현재 결과만으로 얼굴·의상·배경에 작가를 완전히 격리할 수 있다고 보지 않는다.
- 세 artist 태그 비교에서는 첫째가 얼굴·머리카락·전반 화풍, 둘째가 의상·소품·선화·중경, 셋째가 배경·원경·마감에 상대적으로 더 강하게 드러났다.
- 이는 엄격한 지역 분할이 아니라 위치 편향이다. 재현 강도가 큰 태그는 뒤에 있어도 앞선 태그와 강하게 섞이며, 각 태그의 영향 범위도 서로 겹친다.
- 따라서 독자 화풍은 `부위별 작가 할당`보다 `주 화풍 → 보조 디테일 → 배경·마감`의 지배 순서를 설계하는 방식으로 탐색한다.

## `render ... by artist:` 역할 문법

- 사용자 실험에서 `render <대상> by artist:<이름>`은 유효했고, 같은 목적의 `like`보다 `by`가 더 강하게 작동했다.
- 이 문법은 artist의 전역 재현 강도를 단순히 높이는 가중치가 아니다. 해당 artist가 순서상 이미 접근하기 쉬운 범위에서 지정 축으로 영향을 유도하는 `대상 조건형 조절`로 취급한다.
- 상단·중단 artist에 사용했을 때 효과가 강했고 하단 artist에서는 약했다. 특히 하단의 `render coloring by artist:...`는 머리카락 채색에 닿지 못했다.
- 따라서 역할형 추가효과의 현재 작업 모델은 다음과 같다. 측정식이나 내부 구조에 대한 확정 설명은 아니다.

```text
직접 artist 태그 → 전역 스타일 사전조건
render <대상> → 대상의 존재·묘사를 활성화할 가능성
by artist:<이름> → 축과 위치가 허용할 때만 해당 artist 방향으로 조건부 결합
결합 강도 ≈ artist의 상대 위치 접근성 × 대상·축 적합성 × 대상 구체성
```

- 같은 artist를 직접 태그와 역할 문구에 중복하면 역할 효과와 artist 총출현량 증가가 섞인다. 직접 태그 기준선과 역할형을 한 줄씩 교체해 비교한다.
- 아래 판정은 현재 사용자가 시험한 artist·장면·가중치에 대한 경험적 결과이며 NovelAI의 공식 문법 보증이 아니다.

| 지정 축 | 현재 판정 | 관찰 범위 |
|---|---|---|
| `face`, `facial features` | 효과 확실 | 상단·중단 artist에서 얼굴 조형 방향이 강하게 이동 |
| `coloring` | 효과 확실 | 상단·중단에서 강함. 하단 artist는 머리카락까지 제어하지 못함 |
| `background` | 결합문에서 대상 활성화만 관찰 | 없던 배경이 생성되지만 화풍은 지정 artist가 아니라 전체 artist 조합을 따름 |
| `linework` | 효과 미미 | 직접 artist가 가진 전역 선화와 구분 가능한 추가효과가 반복되지 않음 |
| `light and shadow` | 효과 미미 | 역할 문구에 귀속되는 안정적인 추가효과가 관찰되지 않음 |

- 얼굴·채색은 작가 조합 설계에 사용할 우선 후보로 둔다. 배경은 artist 귀속 후보에서 제외하고, 결합문에서 관찰된 생성 효과가 `render background` 단독으로도 반복되는지 분리 검증한다. 선화·명암은 artist 역할 문구 대신 굵기·필압·그림자 경계·광원 방향을 직접 묘사하는 토큰으로 제어한다.
- 상세 입력과 다음 위치×대상 실험은 [V5 Full 프롬프팅 연구](./v5-full-prompting.md)의 A06·A07에 둔다.

## 구조형 문법

- `SECTION:`과 `key: value`는 프롬프트 관리와 속성 인접성에 유효하다.
- 섹션명과 빈 줄은 namespace나 지역 마스크를 만들지 않는다. 섹션명 자체도 모델에 전달되는 토큰이다.
- 대괄호와 중괄호는 구조 표지가 아니라 약화·강화 문법이므로 제목에 쓰지 않는다.
- `scope: face only` 같은 문장은 artist 태그를 얼굴에 격리하지 못했다. 전역 스타일 토큰은 한 `ARTIST RECIPE`에 모은다.
- `ARTIST:`와 `LINEWORK:`처럼 나눈 헤더는 유지보수에는 유용하지만, artist를 해당 축에 격리하는 namespace나 마스크로 보지 않는다.
- 공간 구조는 헤더만으로 생기지 않는다. 전경·중경·원경, 좌우 위치, 실내·외 경계, 광원과 피사체를 명시해야 한다.

## 태그와 자연어의 역할 분담

- 태그형은 평균 스타일과 세부 일관성이 높고 짧지만, 관계·인과와 관리성이 약하다.
- 자연어는 우산과 비, 바람과 목도리, 광원과 피사체 같은 관계를 잘 연결하지만, 단어가 의도하지 않은 시대감·재료·화풍을 불러올 수 있다.
- 현재 가장 유효한 혼합은 `전역 그리기 방식=태그·짧은 속성`, `장면 관계=구조형 자연어`, `인물 정체성=Character Prompt`다.
- 프롬프트가 길어질수록 제어가 단순 합산되지 않고 토큰 경쟁과 스타일 모드 분산이 늘어난다. 약한 `year` 태그나 미세 속성은 긴 프롬프트에서 희석될 수 있다.
- `render <대상> by artist:...`는 얼굴·채색처럼 반응하는 축에서 유효했지만 지역 마스크는 아니다. `like`보다 `by`를 우선하고, 하단 artist의 인물 요소까지 제어한다고 가정하지 않는다.

## 색상

- `hair color:#0a42e7`처럼 대상과 HEX를 붙이는 지정은 유효했다.
- HEX는 정확한 출력 RGB 보증이 아니라 색상 앵커다. 조명, 음영, 주변색, artist 태그와 전역 팔레트 때문에 실제 픽셀색은 이동한다.
- `#0a42e7, ultramarine blue`처럼 HEX 하나에 보조 색명 하나를 함께 두는 방식이 안정적이다.
- 한 역할에는 HEX 하나만 둔다. 투톤은 `main hair color`, `inner hair color`처럼 시각 영역을 나누어 각각 하나씩 지정한다.

## Character Prompt와 Positioning

- Character Prompt는 여러 인물의 외형, 의상, 소품과 상호작용 분리에 강했다.
- Character Positioning은 위치와 대사 귀속을 돕고 특성 bleed를 줄이지만 전역 그림체를 지역별로 고정하지 않는다.
- 공식 V5 발표는 Positioning으로 최대 22명의 서로 다른 인물을 한 화면에 표시한 테스트를 공개했다. 현재 요청 경계의 32개 입력 허용은 32명 안정 표현을 뜻하지 않는다.
- 캐릭터 프롬프트에 `indoors`, `window` 같은 장면 태그를 넣으면 소유권이 흐려진다. 장면은 기본 Prompt, 인물 속성은 Character Prompt에 둔다.

## UC와 역가중치

- UC는 사후 필터가 아니라 또 하나의 conditioning 입력이다. 색조, 배경 밀도, 마감, 페이지 여백과 전역 스타일도 바꿀 수 있다.
- `cyan`, `warm`, `lips`처럼 범위가 넓은 UC는 원하는 머리 반사광, 피부색, 표정까지 억제할 수 있다.
- 같은 개념을 Positive의 음수 가중치와 UC에 동시에 반복하면 단순 합산으로 해석할 수 없다. 먼저 한 경로씩 비교한다.
- 음수 가중치는 단순 삭제뿐 아니라 반대 개념을 유도할 수 있다. 정밀한 제거·반전에는 인라인 음수, 긴 일반 회피 목록에는 UC가 더 적합하다는 것이 공식 권장이다.
- UC 내부 순서에도 같은 위치 효과가 적용되는지는 아직 실험하지 않았다.

## Seed와 평가법

- Seed를 고정하면 이전 형태와 구도를 강하게 재사용하므로 프롬프트의 일반 재현성을 평가하기 어렵다.
- 각 분기는 독립 무작위 Seed 최소 2장, 변동성이 크면 4장 이상으로 확장한다.
- 픽셀 차이가 아니라 기준선 대비 특징 발생률, 저점·중앙값·고점, 유효 결과율과 스타일 모드 수를 비교한다.
- 2장은 후보 선별용이다. 2장 중 1장만 변하거나 기준선과 차이가 모호하면 해당 분기만 4장까지 확장하며, 통계적 유의성으로 표현하지 않는다.
- 역할형 artist 문법은 `전역 작가 유지율`, `목표 축 변화`, `비표적 전역 누출`과 `artist 상대 위치`를 별도로 측정한다.
- 고정 Seed는 문법 분포의 증거가 아니라 미세 디버깅용 보조 수단으로만 쓴다.

## 텍스트 렌더링

- 현재 V5 UI는 큰따옴표 문자열을 수집해 전송 전에 `Text:` 블록으로 재조립한다. 이는 UI 전처리이며 텍스트 인코더의 추론 능력과 구분한다.
- 수동 `text:`를 쓰면 자동 조립 경로가 달라질 수 있으므로 두 방식을 한 실험에서 섞지 않는다.
- Character Prompt와 위치는 화자 귀속을 돕지만 철자, 말풍선 크기, 누락과 하단 여백은 여전히 변동한다.
- `no text` 품질 태그나 UC의 `text`는 실제 렌더링할 짧은 문구와 충돌할 수 있다.

## 만화 신호와 캔버스 구성

- `speech bubble`, 대사와 만화 컷 신호는 장면을 상단 패널처럼 압축하거나 하단에 큰 여백을 예약할 수 있었다.
- 한 장의 일러스트가 목적이라면 `single full-bleed illustration`, `one uninterrupted scene`, `scene fills the entire canvas`처럼 캔버스 사용 방식을 장면 프롬프트에 명시해 대조한다.
- 말풍선 크기와 여백 문제를 동시에 고치려 하면 원인을 분리하기 어렵다. 먼저 무대사 장면으로 전체 화면 사용을 확인한 뒤 대사만 추가한다.

## 언어 지원과 입력 한계

- NovelAI가 공식 지원한다고 밝힌 V5 프롬프트 언어는 영어와 일본어다.
- 중국어, 독일어, 스페인어와 포르투갈어 등도 테스트에서 작동했지만 주 학습 대상이 아니어서 결과가 달라질 수 있다. 한국어는 현재 사용자 실험 근거로만 취급한다.
- V5는 V4.5보다 긴 프롬프트를 지원하지만 공개된 버전 고정 tokenizer artifact와 확정 context token 한도는 확인되지 않았다. 문자 수를 정확한 토큰 수로 환산하지 않는다.

## Qwen 3.5와 지능 비교

- 현재 런타임은 V5의 tokenizer family를 Qwen 3.5로 식별하지만, NovelAI는 텍스트 인코더의 정확한 모델 변형, 파라미터 수, 레이어 구성과 벤치마크를 공개하지 않았다.
- tokenizer는 문자열을 token ID로 나누는 어휘·분할 규칙이다. tokenizer를 공유한다는 사실만으로 Qwen 3.5 LLM의 파라미터나 추론 능력을 공유한다고 볼 수 없다.
- Qwen 3.5 공식 모델군 자체도 0.8B, 2B, 4B, 9B, 27B와 대형 MoE까지 폭이 넓다. tokenizer family만으로 어느 크기인지 역산할 수 없다.
- 확산 모델의 text encoder는 텍스트를 이미지 조건 벡터로 만드는 특수 구성요소다. 대화·코딩·수학 벤치마크로 평가되는 GPT, Claude, Gemini와 지능 등급을 직접 비교할 수 없다.
- 행동 기준으로는 `V4.5보다 관계·긴 자연어·다국어 grounding이 강한 전문 이미지 프롬프트 해석기`라고 부르는 것이 가장 정확하다. 상용 범용 LLM과 동급이라는 표현은 근거가 없다.
